# ts-icon project profile

## Adoption

- Project: NestJS APIs and React/Vite TeamSpeak banner administration, maintained as one product.
- Skill: `project-start` **1.1.0**; engineering baseline **1.1.0**.
- Baseline: [vendored standard](standards/README.md), adopted on 2026-09-10. The project profile records the evidence for ts-icon. Reuse this snapshot on subsequent skill runs; upgrade deliberately.
- Active profiles: Web (TypeScript/JavaScript, JSON/JSONC, CSS), documentation (Markdown/YAML/HTML), core whitespace. Python and Rust are inapplicable.
- Status: formatting and agent-workflow binding adopted; broader startup/version requirements remain partial as listed below.
- Developer platforms: Windows and Linux, also covered by GitHub Actions.

## Local runtime

| Service    | Default bind/port                                            | Configuration                                                      | Readiness                                                         |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Public API | All interfaces, 3000                                         | `IMG_WEB_PORT`                                                     | `/health/live`, `/health/ready`; readiness checks database schema |
| Admin API  | 127.0.0.1 with disabled auth, otherwise all interfaces; 3001 | `IMG_API_PORT`, auth settings                                      | Same health endpoints                                             |
| Frontend   | 127.0.0.1:5173                                               | Vite arguments/config; `VITE_PUBLIC_API_URL`, `VITE_ADMIN_API_URL` | No launcher identity probe                                        |

The existing `scripts/dev.cjs` resolves paths from the checkout, runs Nest watch for both APIs and Vite HMR, and stops owned children on signals or early exit. Windows cleanup uses the owned process tree. Startup has no aggregate readiness deadline, launch identity or prefixed service logging, and Vite can fall back to another port. Therefore process spawn or HTTP 200 alone does not prove successful complete startup.

Default SQLite data is `prisma/dev.db`; `DATABASE_URL` accepts an absolute file URL. Keep existing data intact. Parallel checkout isolation is not a supported combined-launcher contract yet: backend ports, frontend API URLs, frontend port and a separate database must currently be coordinated manually. A complete alternate-port launcher example is pending implementation of shared configuration. Production Compose instead uses nginx `/admin-api` and `/images` proxies and a persistent database volume; see [operations](operations.md).

## Version and release

Root `package.json` is the existing product-version authority (currently 0.9.1); frontend manifest and both lockfile root entries must agree. Retain this single-language, two-package convention rather than introducing another source. Before 1.0, explicitly document breaking API/configuration changes in release notes. Stable three-part versions are the adopted target; prerelease policy remains undeclared even though the CI helper accepts suffixes.

Build output is ignored. The frontend currently has no embedded product version/source revision/mode diagnostic; it cannot prove served bundle freshness. A local transactional updater with downgrade validation and rollback is pending. `scripts/release-version.cjs` is restricted to the main-branch GitHub Actions job and can tag/push; it must never be used for local version preparation.

A push to `main` publishes paired container images after successful dependent jobs when the three required Keycloak repository variables are configured. Missing values skip publication with a job-summary notice while all CI checks still run; invalid nonempty values fail release validation. Release helpers record source SHA, digests and run identity, reuse existing SHA candidates and promote paired aliases. CI container checks and publication currently build separate artifacts; verification of the exact published candidates remains pending. No publication is part of skill adoption.
